# P-Control v2 — план перестройки на базе turizm-control

Рабочий документ. Основан на разборе двух кодовых баз (`p-control`, `turizm-control`)
и техзадания «P-CONTROL TEXNIK TOPSHIRIQ» с двумя схемами процессов.

## 1. Решение

Строим **p-control v2 на фундаменте `turizm-control`**, а не с нуля и не поверх текущего
p-control.

Обоснование:

- Переезд на Filament означает, что весь Vue/Inertia-фронт переписывается в любом случае.
  Значит выбор идёт только между бэкендами — а бэкенд `turizm-control` новее и надёжнее.
- Примерно **70% техзадания там уже реализовано** (см. §2).
- Стек: Laravel 13 + Filament 5 + PHP 8.4 против Laravel 10 + Vue/Inertia.
- 106 файлов тестов (Pest) против фактического отсутствия тестов.

**Принцип работы: без big-bang.** Текущий p-control остаётся в проде и работает,
пока v2 не догонит его по функциональности. Переключение — одним шагом в конце.

## 2. Фундамент: берём как есть

Готовое в `turizm-control`, что закрывает требования ТЗ:

| Требование ТЗ | Что уже есть |
|---|---|
| Дедлайны по этапам (2 / 3 дня) | `ContractApprover::due_at`, `startReview($slaDays)`, `isOverdue()` |
| Уведомления в Telegram | `app/Services/Telegram/*` — бот, меню, роли, состояния диалога, рассылка, логи |
| Хомийлик (спонсорские) контракты | `Sponsor` + `CounterpartyKind::Sponsor` в `ContractType` |
| Авто-закрытие при 70% оплаты | `Payment`, `PaymentStatus`, расчёт статуса по проценту |
| Отдельные роли (в т.ч. «склад») | Filament Shield |
| RU / UZ / EN | `spatie/laravel-translatable` + language switch |
| История по каждому шагу | `mradder/filament-logger` + activity log |
| Версии файлов | `ContractAttachment`, `ContractFiles` |
| Комментарий на каждом этапе | заметки в `ContractApprover` |
| Шаблоны договоров, PDF | `ContractTemplate`, `ContractPdfService`, OnlyOffice |

Ядро процесса — `app/Services/Contracts/ContractWorkflow.php`: транзакции,
`lockForUpdate()` и повторная проверка гейта на каждом переходе (защита от двойного
нажатия и от гонки «веб против Telegram-бота»). Это сохраняем без изменений.

Также переиспользуем: `Department`, `Position`, `Contact`, `Currency`, `Project`,
`Settings`, типизированные Enum вместо int-констант.

## 3. Что вычищаем (специфика туризма)

- `Order` + `OrderScope` + `Filament/Resources/Orders` — выставочные заказы, в p-control не нужны.
- `ProjectType` — пересобрать под категории проектов фонда.
- Номенклатура `ContractType` (аренда площади, стенды, взносы участников) — заменить
  на типы из ТЗ.
- `BankAccount` — оценить, нужен ли фонду; вероятно оставить.

## 4. Что дорабатываем под ТЗ

### 4.1 Три типа контрактов (ТЗ 2.1, 2.4)

Заполнить `ContractType` записями: **Местный / Международный / Хомийлик**.
Для Хомийлик — `CounterpartyKind::Sponsor` (контрагент — спонсор, не контакт)
и отдельная отчётность (ТЗ 2.4).

### 4.2 Конвейер из схемы 1

Целевая цепочка:

| Этап | Кто | Срок | Действие |
|---|---|---|---|
| 1 | Бухгалтерия + Финансист (**параллельно**) | 2 дня | проверка заявки |
| 2 | Финансист → Бухгалтерия | 2 дня | заполняет лот, ИНН, сумму; бухгалтерия сверяет |
| 3 | Юрист | 3 дня | проверка на Xarid.uz, загрузка договора |
| 4 | Финансист (Казна) | 2 дня | прошло → дальше; **не прошло → возврат на этап 1** |
| 5 | Менеджер | 2 дня | загрузка АКТ → оплата |
| — | система | — | при 70% оплаты процесс **закрывается автоматически** |

Что нужно доработать в `ApprovalChain` / `ContractWorkflow`:

1. **Параллельный этап** — сейчас цепочка строго последовательная по `order`.
   Ввести правило: одинаковый `order` = параллельные согласующие, этап считается
   пройденным, когда одобрили все на этом уровне. Затрагивает
   `advanceToActiveApprover()` и построение цепочки.
2. **Возврат на этап 1** от Казны — переход «отклонено на этапе N → цепочка
   пересобирается с начала», с сохранением истории попыток.
3. **SLA per stage** — сейчас `slaDays()` общий; нужен срок, привязанный к этапу
   (2 / 2 / 3 / 2 / 2).
4. **Предупреждение до дедлайна** — напоминание заранее, не только по факту просрочки
   (в ТЗ в блоке «камчиликлар ва такомиллаштириш»).

## 5. Что строим с нуля — складской модуль

Самый большой новый кусок. Логика по схеме 2: **выдача техники сотруднику под
ответственность**, не закупка.

### 5.1 Сущности

- `Asset` — единица техники: наименование, категория, инвентарный номер, штрих-код,
  тех. состояние.
- `AssetCondition` (enum) — Новый / Годный / В ремонт / Списан (ТЗ 1.5).
- `AssetAssignment` — закрепление за сотрудником: кто, когда выдал, статус
  (ожидает подтверждения / принято / на возврате / возвращено), канал подтверждения.
- `AssetWriteOff` — списание с актом и фотографиями (ТЗ 1.5).
- `Warehouse` — если складов несколько.

### 5.2 Процессы

**Выдача** (ТЗ 1.3, схема 2): админ ищет сотрудника → находит товар → закрепляет →
уведомление уходит **в три канала: Telegram-бот / SMS / аккаунт P-Control** →
сотрудник подтверждает → техника переходит под его ответственность.

**Напоминания:** каждые 10 дней, пока техника числится за сотрудником.

**Возврат:** сотрудник нажимает «сдать» → кладовщик подтверждает приём →
техника возвращается на склад.

**Списание:** статус «Списан» → уходит из склада в отдельный список списанных
вместе с актом и фото.

### 5.3 Интерфейс

- Окно склада **делится на две панели** (ТЗ 1.1): слева — что на складе,
  справа — что у сотрудников.
- Экспорт с фильтрами; в файле должно быть видно, **у кого / где** находится
  каждая позиция (ТЗ 1.2).
- Отдельная роль «склад»: видит только складские модули; суперадмин — всё (ТЗ 1.6).

### 5.4 Что переиспользуем

- Telegram-бот — уже готов, добавляем складские сценарии и кнопки подтверждения.
- Напоминания раз в 10 дней — планировщик Laravel + очереди.
- SMS — **новая интеграция** (провайдер уровня Eskiz.uz), отдельный бюджет.
- Штрих-коды — ввод сканером (ТЗ 1.4, выбор модели за Диёрбеком); в мобильном
  приложении сканирование камерой.

## 6. Миграция данных

Из текущего p-control переносим: контакты (с категориями и подкатегориями),
контракты с историей согласования, справочники (валюты, департаменты, должности,
проекты), журнал активности.

Отдельная задача, выполняется в самом конце, до переключения.

## 7. Порядок работ

1. **Фундамент** — новый репозиторий из `turizm-control`, вычистка туризма (§3).
2. **Контракты** — три типа, конвейер из пяти этапов, параллельный этап, возврат от Казны, SLA (§4).
3. **Уведомления** — подключение бота к новым этапам, дедлайны, предупреждения.
4. **Склад** — сущности, выдача, подтверждение по трём каналам, напоминания, возврат (§5).
5. **Списание** — акты, фото, отдельный список.
6. **Мобильное приложение** (Flutter) — параллельно, после появления API.
7. **Миграция данных и переключение**.

На каждом этапе — рабочая система, никакого «полгода в тумане».

## 8. Открытые вопросы

1. Этапы конвейера жёстко зашиты или настраиваются? (по схеме выглядит жёстко — так проще)
2. Схема 1 везде говорит «Заявка №342» — это существующий домен `Application`
   (заявка → контракт → оплата) или сам контракт? Нужно точно развести.
3. Xarid.uz — юрист проверяет вручную или нужна интеграция?
4. SMS-провайдер и сканеры/весы — бюджет и сроки закупки.
5. Склады: один или несколько?

## 9. Риски

- **Складской модуль** — самая большая новая часть, оценивать отдельно.
- **SMS** — внешняя платная интеграция, зависимость от провайдера.
- **Миграция данных** — расхождения схем старого p-control и v2.
- **Соблазн big-bang** — главный риск проекта. Старая система остаётся живой
  до самого конца.
